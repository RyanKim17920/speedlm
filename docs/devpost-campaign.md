## Shared project story

Use this story for HackSocial, VoltHacks, GIBC V2, or BunnieX after adding the
event-specific opening paragraph from the appropriate packet below.

### Inspiration

Teams self-host LLMs so prompts, tool calls, and outputs can stay inside
infrastructure they control. The tradeoff is an optimization gap: their local
server does not automatically learn across a hosted service, its speculative
draft is often frozen and generic, and its expensive GPU sits idle between
traffic bursts. We built SpeedLM to turn that unused local capacity into faster,
workload-specific inference without changing the OpenAI/vLLM workflow or
trusting unverified weights with live responses.

### What it does

Operators keep sending normal OpenAI-compatible requests to a real vLLM
process. SpeedLM records only completed paired exchanges as bounded training
traces inside the operator-controlled environment, then automatically waits
for GPU time that would otherwise sit idle.

After five quiet minutes by default, SpeedLM closes admission atomically,
drains accepted work, and lets vLLM release GPU memory. It snapshots a bounded
traffic window, extracts verifier training signals, warm-starts an EAGLE-3
speculative draft, and evaluates the candidate against the incumbent on a
session-disjoint held-out suite. The candidate is promoted only if it clears
the configured acceptance and throughput safeguards. Otherwise, SpeedLM rolls
back to the incumbent.

If a request arrives during a preemptible stage, it waits at the gateway while
SpeedLM cancels safely and restores a verified serving state. No request is
sent to a sleeping engine or partially trained weights. The full target model
remains authoritative and verifies every emitted token; tuning changes how much
useful draft work it accepts, not which model controls the response.

### Measured result

On Qwen3-8B agentic coding traffic, a session-disjoint gate measured accepted
tokens per verifier step increasing from **2.3051 to 2.6507**: **15.0% more
accepted tokens per verifier step** across **287 held-out contexts × 8
repeats**. In practical terms, the authoritative target accepted more useful
draft work on every verification step.

Wall-clock throughput for those two draft heads ranged from +9.9% to +19.9%
across shared-node runs. That timing channel was non-stationary, so SpeedLM does
not claim a universal 15% throughput improvement. The reproducible headline is
the 15.0% accepted-length improvement; hardware-level speed depends on the
model, traffic, GPU, runtime, and serving conditions.

### How we built it

The system is a Python package and CLI with deliberately separated serving,
data, training, and promotion boundaries:

- A FastAPI/httpx gateway preserves streaming behavior and journals an exchange
  only after its request and response are paired.
- A supervisor launches vLLM on a private loopback port and owns the serving,
  sleep, recovery, and shutdown lifecycle.
- An append-only raw ledger preserves exact exchanges, while a separate
  normalized trace path is bounded and supports configured redaction.
- An idle controller uses atomic admission, confirmation polls, preemption,
  process-group cleanup, recovery, and rollback.
- PyTorch and Speculators/EAGLE-3 workers train outside the live verifier.
- The promotion gate keeps whole sessions on one side of the train/evaluation
  boundary and compares an immutable candidate with the incumbent.

The live-tested environment is an NVIDIA H100 with Python 3.12, CUDA 12.9,
PyTorch 2.11, vLLM 0.25.1+cu129, and Speculators v0.6.0. SpeedLM is a research
preview; other GPU/runtime combinations have not yet been claimed as supported.

### Challenges we ran into

The hardest problem was not starting a training process. It was preserving the
serving contract around that process. Admission and the idle watermark must be
atomic so a racing request is either accepted before quiescence or held outside
the engine. Worker process groups must terminate cleanly. Failed sleep,
training, or benchmarking stages must recover the incumbent. Partial
checkpoints must never reach live serving. Multi-turn agent trajectories must
also stay entirely on one side of the training/held-out boundary.

Benchmarking created a second challenge. Accepted length remained stable across
repeated gates, while wall-clock timing on a shared GPU host did not. We kept
the stable result, exposed the unstable channel, and avoided turning a noisy
timing run into a universal speed claim.

### Accomplishments that we are proud of

- Operators keep their familiar OpenAI-compatible vLLM request workflow.
- Completed serving traffic stays in the operator-controlled environment and
  becomes local training data rather than a submitted dataset.
- After one-time runtime configuration, `--enable-idle-tuning` turns otherwise
  idle GPU capacity into training time.
- The full target model remains authoritative; candidate weights stay isolated
  until a session-disjoint held-out gate permits promotion.
- Requests arriving during tuning never reach a sleeping engine or partially
  trained draft.
- A retained gate measured 15.0% more accepted tokens per verifier step, while
  unstable wall-clock timing is disclosed rather than marketed.

### What we learned

Adaptive inference is as much a systems-safety problem as a model-training
problem. Keeping the verifier authoritative makes the tuned draft disposable:
every new candidate is a measured hypothesis, not a trusted deployment. We also
learned that evidence needs separate acceptance and timing channels. A draft
can improve accepted work per verifier step even when a noisy shared host
obscures the wall-clock effect.

### What is next

- Add bounded admission queues and explicit server-side wait deadlines.
- Validate GPU and runtime combinations beyond the current H100 stack.
- Publish a pinned CUDA container and tagged release.
- Add and validate more trainable verifier/draft profiles.
- Exercise repeated unattended promotion cycles and drift-triggered rollback.
- Publish a sanitized, independently reproducible evidence bundle.

### Paste-ready project description

#### Inspiration

AI teams provision powerful GPUs for peak traffic, but real serving workloads
often include quiet periods. Meanwhile, speculative decoding usually relies on
a frozen, generic draft model that may not match a deployment's real coding,
tool-use, or conversational requests. We wanted to turn otherwise wasted idle
capacity into a practical way for a server to learn its own workload—without
changing the client API or allowing unverified weights to control a response.

#### What it does

SpeedLM wraps `vllm serve` behind a streaming OpenAI-compatible gateway. It
forwards real requests to a real vLLM process and records only completed,
paired inputs and outputs as bounded training traces. After five quiet minutes
by default, it closes admission, drains accepted work, releases serving memory,
and warm-starts an EAGLE-3 speculative draft from the incumbent head.

The candidate must then beat the incumbent on a session-disjoint held-out gate
before atomic promotion. If it fails, SpeedLM rolls back. If traffic returns
during a preemptible stage, the request waits while SpeedLM safely restores a
verified serving state. The full target model remains the verifier for every
emitted token.

On Qwen3-8B agentic coding traffic, accepted tokens per verifier step increased
from 2.3051 to 2.6507—a 15.0% relative improvement across 287 held-out contexts
and eight scored repeats. Shared-node wall-clock results varied, so we report
the stable accepted-length result rather than claiming a universal 15%
throughput gain.

#### Social impact

SpeedLM targets infrastructure waste: idle GPU capacity and generic drafts that
do not reflect the work a community actually runs. By learning from completed
traffic on the serving system users already have, it can lower the barrier to
workload-specific inference efficiency for researchers, student teams, and
smaller AI builders. We have **not** measured energy, emissions, or dollar
savings, so this submission makes no quantitative environmental or cost claim.
Its demonstrated impact is a serving-safe adaptation workflow and higher
accepted length on the evaluated workload.

#### How we built it

We used Python 3.12, FastAPI, httpx, Uvicorn, vLLM, PyTorch, Speculators,
EAGLE-3, CUDA 12.9, and an NVIDIA H100. Separate components own streaming
proxying, paired exchange journaling, redacted normalized traces, idle-state
admission and preemption, draft training, session-disjoint evaluation, and
rollback. The authentic Remotion demo is assembled from real vLLM, curl,
capture, idle-controller, trainer, and gate output.

#### What we learned

Adaptive inference is primarily a systems-safety problem. Training a draft is
the easy part; the difficult work is ensuring a racing request is either
accepted before quiescence or held outside the engine, that partial weights
never reach serving, and that failed or preempted work restores the incumbent.
We also learned to separate stable acceptance measurements from noisy
wall-clock timing instead of stretching one benchmark into a broader claim.

#### What is next

Next we will add bounded request waits, validate more GPU/runtime combinations,
ship a pinned CUDA container, add more trainable model profiles, and publish a
sanitized reproducibility bundle.

### Project title

SpeedLM — Faster Local LLMs From Idle GPU Time

### Elevator pitch

Automatically speeds up local LLMs with idle GPU time while data stays local
and the normal OpenAI/vLLM workflow stays the same.

### Short description

SpeedLM helps self-hosted teams get faster inference from idle GPU time without
changing their OpenAI/vLLM clients. Completed traffic stays in the
operator-controlled environment, every candidate faces a session-disjoint
held-out gate, and the full target model remains authoritative for every token.

### Paste-ready 200–500 word description

Teams self-host LLMs so prompts, tool calls, and outputs can stay inside
infrastructure they control. The tradeoff is that a local server does not
automatically get provider-wide workload optimization. Its generic speculative
draft may not match real coding or tool-use traffic, while its expensive GPU
sits idle between request bursts.

SpeedLM connects those two problems. It wraps `vllm serve` with a streaming,
OpenAI-compatible gateway and records completed input/output exchanges as
bounded training traces. After five quiet minutes by default, it closes
admission, drains accepted work, releases serving memory, and warm-starts an
EAGLE-3 speculative draft from the incumbent head. It then evaluates the
candidate against the incumbent on a session-disjoint held-out suite and
promotes it only if it clears configured safeguards. If the candidate fails—or
new traffic preempts a safe stage—SpeedLM restores verified serving state.

The target model still verifies every emitted token. SpeedLM adapts the draft
that proposes work; it does not give an unverified model authority over the
response. Requests are never routed to a sleeping engine or partially trained
weights.

On Qwen3-8B agentic coding traffic, accepted tokens per verifier step increased
from 2.3051 to 2.6507: a 15.0% relative improvement across 287 held-out contexts
and eight scored repeats. Wall-clock results varied on a shared GPU host, so we
report the stable acceptance result rather than claiming a universal 15%
throughput improvement.

We built SpeedLM in Python with FastAPI, httpx, vLLM, PyTorch, Speculators,
EAGLE-3, CUDA, and an NVIDIA H100. The main engineering challenge was making
request admission, sleep, training, rollback, and preemption one safe lifecycle.
The result is a working research preview of an AI system that improves its own
inference helper from the workload it serves while keeping the verifier in
control.

### Event-fit sentence

held-out evaluation are the core product loop.

### Problem statement

Generic speculative drafts do not reflect the prompts, tools, and response
patterns of a real deployment. GPU idle periods could be used to adapt them,
but naive training on a serving host risks races, downtime, leakage between
training and evaluation, and unverified weights entering production.

### Solution and key features

- Drop-in `speedlm vllm serve` wrapper with the same OpenAI-compatible request
  interface.
- Paired input/output capture with a private raw ledger and bounded normalized
  traces.
- Five-minute default idle threshold, atomic admission closure, and request-led
  preemption.
- Warm-started EAGLE-3 draft tuning rather than training a target model from
  scratch.
- Session-disjoint incumbent-versus-candidate evaluation, atomic promotion, and
  rollback.
- Live status, trace statistics, and measured-gain commands.

### Impact and future scope

SpeedLM demonstrates a path toward inference systems that adapt to real
workloads without changing client applications or weakening target-model
verification. The present research preview is validated on one H100 stack. Next
steps are a pinned container, wider GPU/model validation, bounded request wait
deadlines, more trainable profiles, repeated unattended promotion cycles, and a
public reproducibility bundle.

### Presentation outline

1. Static drafts and unused GPU time: the problem.
2. Streaming vLLM gateway and paired workload capture.
3. Idle-state lifecycle: close, drain, sleep, train, gate, promote or rollback.
4. Authentic demo and Qwen3-8B accepted-length result.
5. Safety boundaries, current limitations, and next steps.
